# Engineering Network — Архитектура бэкенда

> Проектный документ, без кода. Источники: `docs/roadmap-for-team.md`,
> `docs/ai-agent-build-instructions.md`, `PROGRESS.md`, и текущий mock-слой
> данных фронтенда (`src/lib/*.ts`, `src/lib/*-context.tsx`) — он уже
> зафиксировал форму почти всех сущностей на практике, поэтому бэкенд
> проектируется как формализация того, что уже работает на моках, а не с
> нуля. Ссылки на конкретные mock-файлы приведены в разделе "Карта миграции".

---

## 1. Принцип и масштаб

Продукт — сеть для школьников-инженеров, не B2B SaaS с миллионами пользователей.
Нагрузочный профиль скромный (тысячи, не миллионы пользователей на MVP-горизонте).
Из этого следует главное архитектурное решение:

**Модульный монолит, не микросервисы.** Один деплоймый сервис, разбитый на
внутренние модули с чёткими границами (auth, profiles, community, opportunities,
messaging, calendar, admin). Микросервисы на этом масштабе — чистые накладные
расходы (сетевые вызовы между сервисами, отдельный деплой/мониторинг на каждый,
распределённые транзакции там, где сейчас достаточно одной БД-транзакции).
Модульность закладывается на уровне кода (папка на модуль, свой набор моделей,
свой набор эндпоинтов), чтобы при реальном росте можно было вынести конкретный
модуль (скорее всего — messaging или community, если они станут узким местом)
в отдельный сервис без переписывания остального.

## 2. Рекомендуемый стек

| Слой | Выбор | Почему |
|---|---|---|
| Язык/рантайм | Node.js + TypeScript | Фронтенд уже TS — общие типы домена (DTO, enum ролей/действий) можно шарить между фронтом и бэком одним пакетом, не дублировать вручную. |
| API-фреймворк | Fastify или NestJS | NestJS — если нужна структура из коробки под модульный монолит (модули как в описании выше — прямое соответствие). Fastify — если важнее простота и меньше "магии". Выбор не критичен, важнее дисциплина границ модулей, а не фреймворк. |
| БД | PostgreSQL | Данные насквозь реляционные и графовые (голоса, коннекты, эндорсменты — это всё связи между сущностями), Postgres закрывает это нативно + даёт полнотекстовый поиск и `pg_trgm` для похожести текста бесплатно, без отдельного поискового движка на старте. |
| Кэш/сессии/очереди | Redis | Сессии Google-preview (см. раздел 4), rate-limiting, очередь фоновых задач (BullMQ поверх Redis). |
| Файлы (аватары, фото/видео проектов) | S3-совместимое хранилище (S3 / R2 / MinIO для локальной разработки) | Профили и standalone-проекты (Шаг 9) содержат картинки/видео — сейчас на моках это просто строка-URL, в реальности нужен пайплайн загрузки с подписанными URL. |
| Real-time | WebSocket-шлюз (Socket.IO или нативный `ws`) | Нужен для доставки сообщений (Шаг 12) и бейджей непрочитанного (хедер дашборда) без постоянного поллинга. |
| Поиск похожести вопросов (Q&A) | Postgres `pg_trgm` (v1) → `pgvector`/эмбеддинги (v2) | Мок сейчас считает Jaccard-похожесть в браузере по всем вопросам — работает на 4 вопросах, не работает на 4000. `pg_trgm` — прямая замена без нового сервиса. Эмбеддинги — уже отмечены в roadmap как отдельный R&D, не блокирует MVP. |

## 3. API-стиль

REST, ресурсно-ориентированный, версионированный префиксом (`/v1/...`).
GraphQL рассматривался и отклонён для MVP: текущие данные не настолько
глубоко вложенные/разнородные по клиентам, чтобы оправдать сложность
GraphQL-слоя (резолверы, N+1 защита, отдельная авторизация на уровне полей) —
REST ближе к форме, в которой данные уже живут на моках, и его проще
защитить точечными middleware на permission-модель (раздел 6).

## 4. Auth и OAuth — самая нестандартная часть системы

Это не обычный OAuth-бэкенд, потому что спека явно требует **два разных
режима существования пользователя**, и это должно быть видно в архитектуре,
а не только в UI:

### 4.1 GitHub / LinkedIn → полноценный Builder

- Authorization Code flow, минимальный scope (только идентификация — **не**
  запрашивать доступ к репозиториям/связям/постам). Это не только этическая
  декларация из UI-копирайта ("we don't store your data") — это должно быть
  буквально невозможно на уровне запрошенных OAuth-scope, иначе обещание в
  интерфейсе не соответствует тому, что бэкенд технически может делать.
- Из ответа провайдера сохраняется **только**: `provider`, `provider_user_id`
  (для логина/уникальности), `display_name`, `avatar_url`. Токен доступа
  провайдера не хранится дольше, чем нужно для однократного handshake —
  никаких повторных запросов к GitHub/LinkedIn API от имени пользователя.
- Сессия — обычная, персистентная (httpOnly signed cookie + серверная сессия
  или JWT с refresh). Пользователь получает роль `builder` по умолчанию.

### 4.2 Google → stateless preview, не аккаунт

- Тоже OAuth-хендшейк (для верификации, что это не бот), но результат —
  **не строка в таблице пользователей**. Сессия существует только в Redis с
  коротким TTL (или вообще только в подписанной cookie без серверного
  состояния, если не нужен даже realtime для preview-пользователей).
- Это должно быть архитектурным инвариантом, а не соглашением на уровне
  кода приложения: не должно существовать пути записи из Google-сессии в
  постоянные таблицы (users, profiles и т.д.). Технически проще всего
  обеспечить это, если Google-сессия физически не имеет `user_id`,
  который резолвится в постоянную таблицу — только "preview-token" с
  фиксированным, захардкоженным набором прав (см. `PREVIEW_ACTIONS` в
  текущем `src/lib/permissions.ts` — бэкенд должен зеркалить этот же
  список на уровне API, не только фронтенд).
- **Отклонённый вариант:** создавать "теневой" аккаунт для Google-пользователя
  и просто не показывать его в UI-профилях. Отклонено — это ровно то же
  самое хранение данных, которое спека явно запрещает ("не создавать
  аккаунт, не сохранять сессию/данные"), только спрятанное на уровне БД
  вместо UI. Если это когда-то предложат как "оптимизацию" — это конфликт
  со спекой, нужно уточнять с фаундером, не делать по умолчанию.

### 4.3 Роли

`builder | community-lead | admin | super-admin` — хранится на пользователе.
Назначение ролей — только эндпоинт, доступный `super-admin`, **с audit-логом**
(кто, кому, когда назначил роль) — это прямое требование из спеки
("Admin... не self-assign, не по запросу") нуждается в технической гарантии,
а не только в отсутствии кнопки в UI: сам эндпоинт должен на уровне
авторизации проверять `actor.role === 'super-admin'`, а не доверять
клиентской проверке.

## 5. Доменные модели

### 5.1 Profiles (Шаг 9)

Соответствует `src/lib/profile-data.ts` + `src/lib/profiles-context.tsx`.

- **User/Profile** — базовая карточка (discipline, bio, background-пресет,
  Builder-бейдж, online-статус). В моке background — это выбор из
  зафиксированного набора токен-based пресетов (не свободная загрузка
  картинки) — стоит сохранить это ограничение и на бэкенде: пресет = enum,
  не произвольный URL, иначе легко получить рассинхрон с дизайн-токенами
  (Шаг 1/1.6).
- **Skill** — принадлежит профилю, самооценка 1–5. Обновляется только
  владельцем профиля.
- **Project** — standalone-запись (заголовок, текст, картинки/видео,
  список skill-ссылок). Здесь нужен реальный аплоад-пайплайн (подписанные
  URL в объектное хранилище), которого в моках нет вообще (мок принимает
  только текстовые поля).
- **Endorsement** — от одного пользователя к чужому skill/project,
  **причина обязательна** на уровне API-валидации, не только формы (мок
  уже это соблюдает на клиенте — бэкенд обязан продублировать проверку,
  никогда не доверять "обязательности" только фронту).
- Видимость: профили публичны для **Builder**-пользователей (Google-preview
  в эту область не допущен — `profiles:view` уже не входит в
  `PREVIEW_ACTIONS`). Значит эндпоинты профиля требуют полноценной Builder
  сессии, а не просто "любой валидной сессии".

### 5.2 Community — высший приоритет продукта (Шаг 6/7)

Соответствует `src/lib/community-data.ts`.

- **Question** — единый фид без подкатегорий (discipline — просто поле для
  фильтрации/отображения, не отдельное пространство). Ровно 4 действия:
  Approve/Disapprove/Report/Comment — на бэкенде это означает **отдельные
  сущности голосов и репортов**, а не два счётчика на вопросе, как в моке
  (мок хранит `approvals`/`disapprovals` как числа + `myVote` на клиенте —
  это невозможно на сервере с множеством пользователей: нужна таблица
  голосов на пару пользователь-вопрос, чтобы (а) не дать проголосовать
  дважды, (б) дать возможность сменить голос, (в) честно посчитать
  агрегаты). Аналогично Report — нужна отдельная сущность с
  `reporter_id`, чтобы бэкенд мог считать количество репортов и (в
  будущем, не сейчас) вводить порог автоскрытия — этот порог **не
  специфицирован в roadmap**, это открытый вопрос для продукта (см.
  раздел 8), не предполагать значение по умолчанию без подтверждения.
- **Comment** — плоский список внутри вопроса (в моках нет вложенности
  ответов — сохранить эту простоту, вложенные треды нигде не запрошены).
- **Duplicate detection** — сейчас наивное сравнение по Jaccard на клиенте
  по всем существующим вопросам. Не масштабируется за пределы мок-объёма.
  V1 на бэкенде: `pg_trgm`-похожесть по тексту при создании вопроса (запрос
  "top-N похожих" перед сохранением, тот же UX — предупреждение с показом
  найденного похожего вопроса). V2 (отдельный R&D по roadmap): эмбеддинги +
  векторный поиск, если триграммное сравнение окажется недостаточно точным.
- **Webinar** + **WebinarRegistration** — регистрация как отдельная связь
  пользователь-вебинар (мок хранит только `registered: boolean` и
  `attending: number` на самом вебинаре — на бэкенде счётчик посещаемости
  должен быть производным от реальных регистраций, не независимым полем,
  которое можно рассинхронизировать). Создание/редактирование вебинаров —
  только `community:webinars:manage` (Community Lead в рамках своей
  дисциплины — то есть авторизация должна проверять не только роль, но и
  соответствие дисциплины вебинара дисциплине, закреплённой за этим
  Community Lead, если такая привязка вообще вводится — это тоже открытый
  вопрос, roadmap не уточняет, назначается ли Lead на конкретную
  дисциплину или на всю Community целиком).
- **Connection** (My Network) — заявка на коннект между двумя Builder'ами
  со статусами (none/requested/incoming/connected). "N mutual connections"
  на карточке — это агрегат, вычисляемый пересечением принятых связей двух
  пользователей; на масштабе стоит держать в уме, что наивный SQL-джойн на
  каждый рендер списка сети — это N+1-риск, разумный компромисс — считать
  mutual-count лениво/кэшированно, а не при каждом запросе списка.

### 5.3 Opportunities (Шаг 7/8)

Соответствует `src/lib/opportunities-data.ts`.

- **Opportunity** — источник `edugrants` (партнёрский фид) или, потенциально,
  `manual` (если когда-нибудь появится ручное добавление). Партнёрские
  записи не создаются пользователями — нужен **фоновый sync-джоб**,
  который периодически опрашивает edugrants API и делает upsert по
  внешнему `external_id`, а не создание новых записей на каждый запрос
  пользователя (иначе дублирование при каждом обновлении фида).
- Credit-плашка "in collaboration with edugrants" — это не только
  UI-требование, а, вероятно, **условие партнёрского контракта** — стоит
  спроектировать так, будто у edugrants может быть право на аудит показов
  (то есть не помешает базовое логирование обращений к их данным, даже
  если сейчас это не запрошено явно).
- Ранжирование — сейчас rule-based (совпадение по дисциплине пользователя).
  Это остаётся на бэкенде как сортировка/фильтр на эндпоинте листинга.
  AI-matching — отдельный R&D-спринт по roadmap, не блокирует MVP-версию
  этого модуля.
- Доступность: эта единственная секция дашборда, полностью открытая и
  Google-preview, и Builder'ам — значит эндпоинт не должен требовать
  полноценной Builder-сессии, только "какая-то валидная сессия"
  (Builder или preview-токен), в отличие от Community/Profiles.

### 5.4 Direct Messages (Шаг 12)

Соответствует `src/lib/messages-data.ts`.

- **Conversation** (участник A, участник Б) + **Message** (отправитель,
  текст, время, прочитано/нет). 1:1, без групп.
- Открытый месседжинг между **любыми** верифицированными Builder'ами — по
  формулировке спеки ("Открытый месседжинг между верифицированными
  Builder'ами") это **не обусловлено** статусом коннекта в Network. То
  есть DM и Connection — разные, не связанные друг с другом сущности:
  можно написать любому Builder'у напрямую, даже не будучи с ним "connected".
  Это стоит зафиксировать явно, потому что интуитивно кажется, что DM
  должны требовать коннект (как в LinkedIn) — здесь спека говорит иначе.
- **Намеренно без таблиц/пайплайна модерации.** Это не пропуск, а
  зафиксированный продуктовый принцип (см. комментарии в
  `src/pages/dashboard/Messages.tsx` и `docs/ai-agent-build-instructions.md`,
  Шаг 12). Если в будущем кто-то предложит добавить сканирование сообщений
  или очередь модерации — это прямой конфликт со спекой, нужно
  переспрашивать у фаундера перед реализацией, не добавлять по умолчанию
  "на всякий случай" (например, "для безопасности" или "по запросу
  родителей/школы" — вопрос может звучать разумно, но это осознанное
  решение продукта, а не забытая фича).
- Доставка в реальном времени — WebSocket-канал на пользователя;
  бейдж непрочитанного в хедере дашборда должен читать тот же источник
  правды (количество недоставленных/непрочитанных сообщений), а не
  отдельный независимый счётчик.

### 5.5 Competition Calendar (Шаг 10)

Соответствует `src/lib/calendar-data.ts`.

- **Competition** (название, локация, дисциплина, дедлайн). Сейчас чистый
  мок без источника данных вообще. Открытый вопрос: это ручной
  контент (курируется Admin/Community Lead через админку) или со временем
  тоже партнёрский фид (по аналогии с edugrants)? Roadmap не уточняет —
  предлагается v1: простая CRUD-таблица, курируемая вручную ролью
  Admin/Super Admin, без внешнего API, до появления явного запроса на
  партнёрскую интеграцию.
- Логика "только даты от today() и далее" — это фильтр на уровне запроса
  (`deadline >= now()`), не то, что нужно вычислять на клиенте, как сейчас
  в моке — иначе на разных клиентах с разным локальным временем возможны
  расхождения, что именно "сегодня".
- "Daily Reminders" — подразумевает foновую задачу (ежедневная выборка
  "дедлайн через N дней" для пуша/значка), то есть тот же джоб-планировщик,
  что и для edugrants sync, только на другом расписании.

### 5.6 Deferred / не проектируется в деталях сейчас (Шаг 13)

- **Project Onboarding flow** — только точка расширения (`POST
  /v1/users/:id/onboarding` как стаб на будущее), реальная модель не
  проектируется, пока не будет решено, что именно собирается на этом шаге
  (дисциплина, аватар, первые skills — предположительно, но не
  зафиксировано в roadmap).
- **Terms of Service / Privacy Policy** — по сути не бэкенд-задача, кроме,
  возможно, поля `tos_accepted_at` на пользователе для юридической
  фиксации согласия перед публичным релизом.
- **Post a Project (полный флоу)** — при реализации встанет вопрос,
  использовать ли ту же таблицу `Project`, что и standalone-проекты в
  профиле (раздел 5.1), или заводить отдельную сущность "заявка на
  проект" с своим жизненным циклом (набор команды, статус). Не решать
  заранее — решение стоит принимать вместе с реальным UX-флоу, которого
  пока нет даже на макетах.

## 6. Авторизация — бэкенд как источник истины

Фронтенд уже держит центральную модель прав в `src/lib/permissions.ts`
(`Action` enum + функция `can(user, action)`). Это **не должно** оставаться
только клиентской проверкой при переходе на реальный бэкенд:

- Каждый эндпоинт независимо проверяет `can(actor, action)` на сервере,
  используя тот же набор действий, что и фронтенд (в идеале — один общий
  пакет типов/констант, шарящийся между фронтом и бэком, чтобы список
  действий не разъезжался в двух местах).
- Клиентские проверки (`RequireAction`, скрытие пунктов меню) остаются —
  это UX, не защита. Настоящая граница — на API.
- Google-preview — не роль, а отдельный статус с фиксированным списком
  разрешённых действий (`community:read-overview`, `opportunities:view`),
  который не может быть расширен ни при каких обстоятельствах без
  прохождения полноценного OAuth (см. раздел 4.2).

## 7. Карта миграции: мок → сервис

| Мок сейчас (фронтенд) | Будущий модуль бэкенда |
|---|---|
| `src/lib/auth-context.tsx` | Auth-модуль: OAuth callback, выпуск сессии |
| `src/lib/permissions.ts` | Общий Authorization-пакет (шарится фронт+бэк) |
| `src/lib/profile-data.ts`, `src/lib/profiles-context.tsx` | Profiles-модуль |
| `src/lib/community-data.ts` | Community-модуль (Q&A, Webinars, Network) |
| `src/lib/messages-data.ts` | Messaging-модуль + WebSocket-шлюз |
| `src/lib/calendar-data.ts` | Calendar-модуль |

Мок-слой не выбрасывается в момент подключения бэкенда — он остаётся
полезен как: (а) контракт форм данных для API-ответов (уже проверенная
форма, менять только по необходимости), (б) fallback для локальной
разработки фронтенда без поднятого бэкенда.

## 8. Открытые вопросы (не решать по умолчанию — уточнять)

Пересекаются с `PROGRESS.md`, но специфичны для бэкенд-проектирования:

1. Порог/политика авто-скрытия вопроса по числу репортов в Q&A — не
   специфицирован нигде, нужен продуктовый ответ, прежде чем встраивать
   любую автоматическую модерацию (важно не спутать с DM — там модерация
   явно запрещена; для Q&A запрет explicit не зафиксирован, но и
   разрешение — тоже, это именно открытый вопрос, а не решённый).
2. Назначается ли Community Lead на конкретную дисциплину или на всю
   Community — влияет на модель авторизации для управления вебинарами.
3. Competition Calendar — ручной контент навсегда или будущий партнёрский
   фид, как edugrants — влияет на то, стоит ли сразу проектировать под
   sync-джоб или это избыточно для MVP.
4. edugrants API — контракт/SLA/лимиты не подтверждены (тот же риск, что
   уже отмечен в roadmap) — влияет на частоту sync-джоба и на то, нужен ли
   кэш-слой перед показом пользователю при недоступности партнёрского API.
5. OAuth-бэкенд (реальный token exchange) — по roadmap отдельная
   незапланированная работа, блокирующая переход всех Builder-фич с
   мок-сессий на настоящие; весь раздел 4 проектируется заранее именно
   для того, чтобы это подключение не потребовало пересмотра модели
   ролей/сессий, когда до него дойдёт очередь.
