# Engineering Network — Roadmap разработки

> Основано на спецификации `context.md` + PDF welcoming page.
> Разрешённый конфликт: кнопка **Settings** размещается **top-right** на всех страницах
> (обоснование см. в сопроводительном сообщении — единообразие с notification/message
> badges в дашборде и конвенция top-right для account/settings меню).
>
> **Разрешённый конфликт (07.07.2026):** Сайдбар (dashboard, desktop) сворачивается
> кнопкой в icon-only rail, по умолчанию развёрнут, выбор персистится (localStorage).
> Причина: фаундер просил "сайдбар не должен мешать на страницах". Дословное
> "исчезает на всех pages" отклонено — ломает навигацию (нельзя перейти между
> разделами, если меню пропало). Компромисс: collapse-в-иконки даёт больше места
> контенту, сохраняя навигацию. Активный пункт подсвечен в обоих состояниях,
> tooltips обязательны в свёрнутом. Mobile — без изменений (гамбургер/off-canvas
> drawer). Согласовано: агент → подтвердить с фаундером.
>
> **Обновление от фаундера (03.07.2026):** прямое использование 21st.dev-компонентов
> отменено — "make it as good as possible, down to the details, humanly possible".
> Все ссылки на 21st.dev ниже по тексту читаются как функциональные референсы
> (что за паттерн нужен), а не как обязательный код для установки. Добавлена
> новая Фаза 1.5 — кастомный визуальный дизайн через Claude Design.

---

## Как читать этот план

- Этапы идут в порядке зависимостей: нельзя эффективно строить Фазу N+1, пока не закрыта Фаза N (за редкими исключениями, отмеченными как "можно параллелить").
- Community — заявлен в спеке как **высший приоритет продукта**, поэтому он идёт сразу после базовой инфраструктуры и авторизации, а не в конце.
- Все пункты, помеченные **[DEFERRED]**, специально не реализуются — только оставляются "хуки" (пустые роуты/кнопки без функциональности), как явно указано в спеке.

## Фаза 0 — Фундамент проекта (1–2 дня)

**Цель:** рабочий скелет, на который можно накатывать фичи.

1. Инициализация проекта: React + TypeScript + Vite/Next.js.
2. Установка Tailwind CSS.
3. Настройка shadcn/ui, создание `/components/ui`.
4. Установка `next-themes` (dark/light) и `framer-motion`.
5. Базовый роутинг (welcome → auth → post-auth shell).
6. Настройка окружения: `.env`, линтер, форматтер, git-репозиторий.

**Definition of done:** пустое приложение запускается, роутинг между `/`, `/auth`, `/dashboard` работает, shadcn CLI подтверждён рабочим.

## Фаза 1 — Дизайн-система (2–3 дня)

**Цель:** зафиксировать два разных визуальных языка до того, как на них начнут собирать страницы.

1. Токены цвета: cornsilk-палитра для /, /help, /auth; deep-dark + radial gradient для /dashboard/*. Вынести в Tailwind config / CSS-переменные, а не хардкодить по компонентам.
2. Общий hover-паттерн: white-tinted hover на всех interactive-элементах дашборда — сделать как переиспользуемый Tailwind-класс/variant.
3. Подключить `next-themes` provider на уровне layout.
4. Прототип обеих "оболочек" (light shell, dark shell) без контента — просто фон + переключение темы, чтобы визуально утвердить до реализации логики.

**Решение (04.07.2026):** тема определяется РОУТОМ, не статусом входа.
Google-preview пользователи заходят в /dashboard/community и
/dashboard/opportunities без полноценного логина, но видят ту же тёмную
тему, что и Builder'ы — не cornsilk. Не завязывать выбор темы на
"залогинен ли пользователь".

**Definition of done:** можно переключаться между двумя пустыми layout-заготовками и видеть корректные фоны/темы.

**Может идти параллельно с Фазой 0 (хвостом), если в команде есть отдельный дизайнер/фронтендер.**

## Фаза 1.5 — Custom UI design (Claude Design) (3–5 дней)

Зависит от: Фаза 1 (дизайн-токены уже определены на уровне cornsilk/dark-тем).
Блокирует: все последующие фазы, где раньше стоял 21st.dev-компонент как эталон.

1. Спроектировать в Claude Design кастомные макеты для: welcome-страницы
   (анимированный фон, headline, feature-секция), post-auth shell (сайдбар,
   хедер), signup/login формы, Q&A-диалога, Help-аккордеона, Profile-страницы,
   Competition Calendar.
2. Зафиксировать итоговые макеты и токены (цвета, шрифты, spacing, motion)
   как единственный источник истины для фронтенд-разработки — 21st.dev URL
   в остальных фазах ниже больше не читаются как "обязательный пакет",
   только как описание нужного поведения (что за компонент нужен функционально).
3. Согласовать макеты с фаундером до начала кодирования — дешевле поменять
   макет сейчас, чем переписывать готовый код позже.

**Definition of done:** есть утверждённый набор экранов/токенов, на которые можно
ссылаться при код-ревью вместо "похоже это или нет на 21st.dev-референс".

## Фаза 1.6 — Компонентный слой (1–1.5 дня)

Зависит от: Фаза 1 (токены), Фаза 1.5 (визуальный язык утверждён).
Блокирует: все фазы сборки экранов (2, 4–10) — компоненты должны существовать до того,
как на них начнут собирать страницы.

**Зачем (важно для команды):** shadcn-примитивы headless — без вида. Токены задают
атомы (цвет/шрифт/spacing), но не форму компонентов. Без этого слоя каждый экран
одевает кнопки/карточки по-своему → визуальный разнобой (напр. Register и Registered
в разных стилях, карточки разной отделки). Это фактическая причина расхождений,
замеченных на ранних экранах.

1. Привести к токенам и достроить существующие компоненты (cva поверх shadcn):
   - `button.tsx` уже есть → добавить состояние **done** (Registered/Connected:
     прозрачный фон + акцентная рамка + галочка, НЕ серый disabled); вариант
     `accent` перевести на золото тёмной темы (`gold-dark`), т.к. `corn-700`
     тускнеет на тёмном фоне.
   - `card.tsx` уже есть → убрать хардкод (`text-[#2A2118]`, `bg-white/65`),
     сделать тема-зависимым через токены.
   - **Создать заново** (не существуют): `chip.tsx`, `avatar.tsx`, `label-caps.tsx`.
   - Input — привести форм-поля к токенам обеих тем.
   Полная спека — Шаг 1.6 в инструкции для агента.
2. Ключевой момент: пары Register↔Registered, Connect↔Connected — одна кнопка в двух
   состояниях (accent → done), не две кнопки. «Выполнено» = акцентная обводка +
   галочка, читается как достижение, НЕ как серый disabled.
3. Токены в конфиге: достроена dark-палитра (`dark.surface/surface2/text/muted`),
   добавлено второе золото (`gold-dark #C79A3A`) для тёмной темы. Значения снять
   пипеткой с реальных экранов и сверить (см. tailwind-config-patch).

**Definition of done:** один Button со всеми вариантами/состояниями, один Card, Chip,
Avatar, Label, Input — на токенах, в обеих темах. При код-ревью экранов проверяем:
элемент собран из компонента, а не нарисован заново.

## Фаза 4 — Signup / Login (3–5 дней, самая критичная фаза для доверия к продукту)

Зависит от: Фаза 0, Фаза 1.

1. Взять `AuthForm` компонент **as-is** из спеки как базу (Card/Button/Input/Label уже включены).
2. Реализовать зависимости: `next-themes`, `lucide-react`, `@radix-ui/react-slot`, `class-variance-authority`, `@radix-ui/react-label`.
3. Рескин под референс-скриншот:
   - GitHub / LinkedIn кнопки с бейджем "Full access".
   - Google кнопка с бейджем "Limited preview".
   - Подзаголовок формы. **Решение (07.07.2026):** "Join eengineer" — чуть
     крупнее обычного текста, но не перегруженный размер.
   - Warning-баннер, объясняющий ограниченный доступ Google.
     **Решение (07.07.2026), финальный копирайт:** "Google only gets read-only
     preview access. Everything else is locked until you register through
     Github or Linkedin. However, neither reuses or stores your data. It is
     just for the sake of confirming you are a real person."
4. Настроить OAuth-флоу:
   - GitHub/LinkedIn → полный Builder-статус (реализуется здесь как заглушка/мок до подключения бэкенда, если бэкенд ещё не готов — но UI-состояния должны существовать).

5. UI-копирайт должен явно доносить: "мы не храним данные из GitHub/LinkedIn — это только сигнал доверия".

**Definition of done:** оба флоу (Builder / Google preview) визуально и по состоянию отличимы, копирайт про приватность на месте.

**Технический риск, который стоит проговорить в команде:** реальная OAuth-интеграция (backend token exchange, сессии) — отдельная под-задача, не блокирует фронтенд-часть, но блокирует "настоящий" post-auth доступ. Можно параллелить: фронтенд на моках, бэкенд на реальном OAuth.

## Отклонённые паттерны — не предлагать повторно

Эти решения приняты после critique-циклов и зафиксированы, чтобы не
возвращаться к ним в будущих сессиях (Claude Code не помнит прошлые
разговоры между сессиями, если это не записано здесь):

1. **Декоративная схемотехника** (шестиугольники, линии-соединения,
   абстрактные узлы) как filler для пустых зон — отклонено дважды
   (welcome-страница, правая колонка дашборда). Не несёт информации,
   generic для любого tech-продукта, на дашборде прямо противоречит
   правилу "no grid lines/path lines".
2. **Orbit-анимация** (вращающиеся по кругу аватары/иконки) как способ
   заполнить пространство — рассмотрено и отклонено для правой колонки
   дашборда: непрерывное вращение — тот же класс "look busy" декора,
   плюс accessibility-риск (prefers-reduced-motion), плюс нечитаемые
   имена в движении.
3. **Решение по правой колонке дашборда (финализировано):** пространство
   над карточкой вебинара/профиля остаётся ПУСТЫМ осознанно — не
   заполняется декором. Заполнится органически контентом из Шага 7-8
   (Community/Opportunities), когда они будут реализованы. До этого —
   не предлагать замену.
   Примечание: этот же принцип «пустота = воздух» относится ТОЛЬКО к
   welcome/editorial-экранам и к этой конкретной зоне. На дашборде-контенте
   (лендинг Home, Community-фид) пустой центр — это НЕ воздух, а признак
   нежилого продукта; там центр наполняется реальным контентом (лента,
   проекты, рекомендации), а не оставляется пустым и не декорируется.
4. **One-off кнопки / карточки / чипы — запрещено.** Любой повторяющийся
   UI-элемент (Button, Card, Chip, Avatar, Label, Input) собирается ТОЛЬКО
   из компонентного слоя (Фаза 1.6 / Шаг 1.6 у агента), а не рисуется заново
   на конкретном экране. Причина: именно это давало разнобой (Register vs
   Registered в разных стилях, карточки разной отделки). Нужен новый вариант —
   сначала добавить в спеку компонента, потом использовать. Не изобретать вид
   на месте.
5. **Хардкод цвета/размера в обход токенов — запрещено.** Никаких прямых
   hex/px/font-family в компонентах. Всё ссылается на именованные токены
   Шага 1. Правка оттенка/размера идёт в токен (одно место → все экраны),
   а не в отдельный компонент.

## Ключевые риски

1. **OAuth-бэкенд** может отставать от фронтенда — договориться о моках заранее.
2. **Duplicate-question detection** в Q&A — недооценённая по сложности фича, начать с простого решения.
3. **edugrants API** — зависимость от внешнего партнёра, уточнить SLA/доступность ключей до Фазы 7.
4. **AI-matching** (Opportunities, возможно Community) — легко недооценить срок, лучше выделить в отдельный R&D-спринт.
5. Юридический текст (Terms/Privacy) сознательно отложен — не блокирует разработку, но нужно не забыть перед публичным релизом.
